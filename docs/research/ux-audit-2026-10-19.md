# Kitden UX audit

Research checked: 2026-10-19.

Audience confirmed by the owner: developers who use several AI coding clients.

## Main decision

Keep Kitden's calm visual identity and client comparison table. Improve the decisions inside the existing flows: which item this is, where it comes from, which clients change, what was verified, and how to undo it. These changes offer more value than adding new navigation or decorative motion.

The main product promise should be easy to experience: understand your setup, resolve a problem, review the exact effect, apply safely, and recover if needed.

## Evidence and limits

- Visual evidence: all 26 pages of `/Users/amandawoodward/Downloads/Kitden design.pdf`. These are 13 light/dark pairs, not 26 different workflows.
- Product evidence: `AGENTS.md`, `docs/design.md`, the web UI source, and the views that build its data.
- Assessment A: an independent visual and heuristic review by `design_assessment`, completed before the parent received detector findings.
- Assessment B: an independent implementation and sandbox browser review by `implementation_assessment`. Its results are recorded in the implementation section below.
- External evidence: primary design guidance, official competitor documentation, and public product screenshots. Competitors were not installed or benchmarked against Kitden.
- This is an expert audit, not a user study, WCAG certification, runtime health audit, or measured satisfaction score. Source code can establish an intentional delay; it cannot establish how a spring feels on a user's computer.
- No real client settings were changed. Recommendations below are proposals, not implemented UI changes.

## What works

1. **Comparison fits the task.** The Load map puts an item and its clients on one row. Keep this structure for developers who need to compare configurations.
2. **Changes are reviewable and reversible.** Preview, Apply, backups, verification, Cancel, and Undo form a strong basis for trust. Undo also exists in Changes; it is not limited to a temporary toast.
3. **The visual system is coherent.** The house mark, warm accent, neutral surfaces, restrained borders, and two themes feel like one product. Empty space on Overview and Changes does not need filler.
4. **Useful details already exist.** Source information, item contents, exact file changes, errors, and recovery paths are implemented. File changes are collapsed by default. The expanded diff in the PDF is not evidence that technical details are always exposed.

## Priority recommendations

Severity: P1 affects a core decision or trust; P2 creates recurring friction; P3 is polish. No production incident or data loss was established by this audit.

### P1: Make the item identifiable before Add

**Evidence:** PDF pages 9-12 and 19-20. Names, descriptions, and distinguishing marketplaces are truncated while `Can add` and `Via Claude Code` repeat across large cells. Similar Canva, Figma, and Hyperframes entries are hard to distinguish at a glance.

**Change:** Keep a compact comparison table. Give the item column roughly 40-45% of the working width as a starting prototype, with up to two lines of description and a short source label. Keep the client columns compact. Never truncate both the item name and the only field that distinguishes it from a same-name item. Preserve the full identifier in Details and the accessible name.

The current source sets the first column to 34%; the PDF appears narrower. Review the current browser before choosing a percentage. The durable requirement is readable identity, not a fixed column ratio.

**Acceptance:** A developer can distinguish two same-name packages and choose the intended source without opening each row in turn. Test at a laptop width and with browser zoom.

### P1: Show every effect in Add and Preview

**Evidence:** Pages 13-14 show a very sparse Add panel with clients already selected. Pages 15-16 name Claude Code and Codex. Pages 17-18 also show a changed Cursor state. `discover.js` preselects all available target clients and separates the rich Details panel from the short Add form.

**Change:** Put the useful item description, source, selected clients, extra marketplace, and inherited effects together in the Add panel. Keep paths and commands in Details. Reuse the same summary in Preview.

For example, if established by the actual setup:

> Add agent-sdk-dev
>
> Source: claude-plugins-official
>
> Add to: Claude Code
>
> Cursor will also load this through Claude Code.
>
> Preview change

If no target client is implied by the user's entry point, ask for the client selection in this existing form. Avoid silently assuming every available client is wanted. Do not add another confirmation dialog.

Keep a clear Add action in the item Details panel so a user who inspected the source can continue without closing and finding the row again.

**Acceptance:** Before Apply, users can name every directly and indirectly affected client, any marketplace being added, and the expected state after reload. The interface must not imply that an unselected client is unaffected when inheritance says otherwise.

### P1: Match the gateway action to the safe migration path

**Evidence:** Pages 1-2 count direct servers among things needing attention, including local servers that must stay on the Mac. Pages 5-6 tell the user to add a server to the gateway before removing its direct entry, yet the prominent action is Remove. Pages 21-22 already offer a move flow.

**Change:** Distinguish a broken setup from an optional routing improvement. Present duplicates and unreadable files as problems. Present eligible direct connections as a separate opportunity. Treat local-only servers neutrally.

Use `Direct connection` instead of a warning-shaped `Not via gateway` unless a specific policy or actual duplicate makes it a problem. Use a precise count of connections or unique servers, consistently.

In item Details, lead with the supported safe move action. If the connected gateway cannot accept that move, explain the limitation and offer the gateway's next step. Enable removal as the cleanup step only after the replacement can be confirmed, or offer removal separately with its actual consequence clearly stated. Do not promise a new Obot capability merely by renaming a button.

**Acceptance:** A user can move an eligible server without losing its only usable connection. The preview identifies destination, removals, affected clients, and how Undo works.

### P1: Tell the truth about saved, running, and uncertain states

**Evidence:** The UI uses `Loads`, `Installed`, `Applied`, and `everywhere`. The data model derives effective configuration from saved settings. The successful result can still require a client restart. `panel.js:517` says `Nothing was changed by this page` when the request throws, although a request can reach the server and lose its response.

**Change:** Distinguish configuration evidence from runtime evidence. A small explanation such as `Based on saved settings` can set the correct expectation. Use explicit scope words: `Global settings` and `This project`. Do not replace `everywhere` mechanically with `all projects` where project overrides can change the result.

After Apply, keep the exact client-specific reload or restart instructions visible in the result or change detail. Keep Undo in Changes. Do not invent a restart detector; if completion cannot be observed, present an instruction the user can dismiss, not a live health state.

When the response is lost, say `Could not confirm the result. Check Changes before trying again.` Reconcile the operation by its ID before reporting success, failure, or retrying.

**Acceptance:** A lost response never produces a false claim of no write. A successful saved change never implies that a running client has already reloaded it. Restart instructions remain findable after the toast disappears.

### P1: Keep the displayed project and data freshness truthful

**Evidence:** Source-confirmed path, not fault-injected in the browser: `store.js:84-90` keeps the last model when a request fails. `app.js:81-85` still advances Scanned after that guarded reload. `map.js:45-58` can show the newly selected project above the previous model, with an error banner only when there is no model.

**Change:** Store the loaded project and last successful read time with the model. When refresh fails, retain the correct old scope label and show a persistent warning, or show the new scope as unavailable. Do not present old data as a successful new scan. Review changes against the same identified scope.

**Acceptance:** After changing project and interrupting the request, the UI never labels old-project data as the new project. Scanned reflects the last successful read. Retry has a clear result.

### P2: Make Details and search behavior predictable

**Evidence:** On Load map, Discover, and Changes, whole rows open details but their appearance does not clearly advertise this. Gateway already has explicit Details actions. Search uses one placeholder but searches the catalog in Discover and moves to Load map elsewhere (`app.js:195`).

**Change:** Use a consistent understated affordance: a clickable name and/or chevron, with keyboard access and an explicit accessible name. Keep Add and Undo as separate actions. Use contextual search labels such as `Search your setup` and `Search available plugins and skills`. Preserve the query and filters when returning from Details.

**Acceptance:** A first-time Kitden user can find an item's source, inspect a past change, and predict the scope of search without instructions.

### P2: Preserve keyboard focus through tabs and review

**Evidence:** Reproduced in the sandbox browser: selecting a Load map or Discover tab left focus on BODY. The Review focus loop skipped `Show file change` after reaching Cancel and Apply. The focus-stop selector in `panel.js:682` omits native `summary` elements; `app.js:34-41` restores table-row focus but not tab/filter focus after rendering.

**Change:** Restore focus to the semantic control after updates. Give tabs a consistent keyboard pattern. Include visible native focusable controls in the dialog cycle, including summary, and exclude hidden content. Preserve the current working row focus on return from Apply.

**Acceptance:** Use only keyboard input to change type, filter the table, open an item, read its diff, cancel, apply, and return. The focus stays visible and all controls remain reachable.

### P2: Let the user continue as soon as the verified result is ready

**Evidence:** `panel.js:592` pads a successful Apply to at least 520 ms, then `panel.js:597` waits at least another 450 ms before closing the review and returning control. A fast request therefore has about a 970 ms floor before that return, excluding slower reload and visual transitions. These waits do not check reduced-motion preference.

**Change:** Remove the forced completion floor. Show pending feedback immediately; show the verified result as soon as it is available. Let a short success cue run without delaying the next action. Keep double-submit prevention tied to the operation state, not the animation.

**Acceptance:** On a fast sandbox operation, the interface does not wait for a timer before allowing the next valid action. Reduced motion removes movement and artificial wait. Errors remain readable.

## Motion review

The following durations are proposed starting values for Kitden, not accessibility standards or proof of an ideal feel. Apple treats motion as feedback and context; Emil Kowalski's exercises emphasize purpose, frequency, and interruption. [Apple HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion), [Train Your Judgement](https://emilkowal.ski/ui/train-your-judgement). Checked 2026-10-19.

| Before | After | Why |
| --- | --- | --- |
| Apply pads to 520 ms and holds success for another 450 ms | No artificial floor; result follows verification; a brief cue may continue without blocking | The user should wait for work, not for a presentation sequence. |
| Drawer moves for 320 ms; children rise for 360 ms with up to 120 ms delay | Prototype 220-260 ms for the drawer, with content immediately readable; no repeated content stagger | One spatial cue is sufficient. A 320 ms drawer alone is not a defect; stacked effects are the concern. |
| File diff lines appear over up to about 512 ms | Reveal the diff together; optionally use a short opacity transition | The diff is information the user deliberately opened to inspect. |
| Error button shakes 10 px over 360 ms | Prefer a persistent inline explanation and focused recovery action; remove the shake or reduce it after testing | The error needs a resolution more than extra movement. |
| Frequent navigation can move indicators and crossfade content | Keep selected state immediate; simplify repeated navigation, especially keyboard paths | Preserve the feeling that the interface follows input. |
| State label swaps can blur | Keep important result words readable during the change | Clear status matters more than a decorative morph. |

**Verdict:** retain the motion system, but block further motion polish until the artificial Apply wait and any confirmed focus interruptions are fixed. Do not fail every duration above 300 ms mechanically. Small layout animations permitted by the project need profiling, not a blanket performance claim. A dot filling from zero is also different from a popover scaling from zero.

The resting style must remain correct without animation, rapid open/close should not produce stale states, and reduced motion must keep all information available. Do not add looping gateway traffic indicators unless traffic is actually observed.

## Visual and accessibility refinements

- Keep the house mark and its fixed brand color, system font, neutral panels, and 6-10 px corner family.
- Give item names and descriptions priority over repeated metadata. A modest 14 px text prototype may be worth testing against the current 13 px base; do not enlarge every table cell blindly.
- Use more comfortable hit areas for frequent actions, for example 32-36 px high where space allows, while preserving useful table density. Keep primary Apply comfortably distinct from Cancel. These are design targets, not WCAG minimums.
- WCAG 2.2 AA target size is 24 by 24 CSS pixels with specified exceptions, including spacing; a visual glyph alone does not establish hit size. Measure the actual controls. [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). Checked 2026-10-19.
- Normal text generally needs 4.5:1 contrast; large text 3:1, with stated exceptions. [W3C text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Checked 2026-10-19.
- Calculations from current color tokens: white on the primary action is 5.30:1; light muted text on white 5.36:1; light muted text on the inset 4.78:1; dark muted text on the panel 6.88:1. There is no basis for calling the entire design low contrast.
- The white success label on the dark theme green is 2.27:1; on the light theme green it is 4.38:1. Give status text a readable foreground/background pair. The temporary button remains disabled, so do not label this an unconditional WCAG failure without considering the inactive-control exception and its status role.
- Check visible focus, hidden panels, collapsed content, return focus, and no focus covered by the fixed bar or drawer. [W3C modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [Focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html). Checked 2026-10-19.
- On narrow desktop windows, keep horizontal scrolling local to the comparison table. Check browser zoom, long identifiers, drawer footer reachability, and retained column context. A full mobile redesign is not the first priority for a local developer tool.

## Guidance behind the recommendations

1. **Visibility, control, recognition, and recovery.** Use an understandable state, predictable action, and clear exit. [Nielsen's usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/). Checked 2026-10-19.
2. **Progressive disclosure.** Hide paths and commands, but keep the information required to choose the right item and understand its effects. Hiding critical consequences is not simplification. [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/). Checked 2026-10-19.
3. **Review and completion are separate jobs.** Review explains what will change. Completion explains what happened and what remains. [GOV.UK: Check answers](https://design-system.service.gov.uk/patterns/check-answers/), [Confirmation pages](https://design-system.service.gov.uk/patterns/confirmation-pages/). Checked 2026-10-19.
4. **Controls imply behavior.** A switch normally implies an immediate change. For a change that requires Preview and Apply, prefer an action such as `Turn off...` or selection controls within a reviewable form. Preserve Kitden's safety sequence. [NN/g: Toggle-Switch Guidelines](https://www.nngroup.com/articles/toggle-switch-guidelines/). Checked 2026-10-19.
5. **Responsiveness is part of control.** Immediate input feedback and short task delays support continuity. The classic response thresholds are guidance, not a reason to add artificial minimum waits. [NN/g: Website Response Times](https://www.nngroup.com/articles/website-response-times/). Checked 2026-10-19.
6. **Measure the user's goal.** Select signals for completion, errors, confidence, and satisfaction before choosing metrics. [Google Research: HEART](https://research.google/pubs/measuring-the-user-experience-on-a-large-scale-user-centered-metrics-for-web-applications/). Checked 2026-10-19.

## User validation plan

Recruit five or six developers who use at least two supported clients. Include people seeing Kitden for the first time and people comfortable with MCP. Use sandbox configurations. A small round can reveal recurring obstacles; it cannot support precise population success-rate claims.

Give tasks without explaining the interface first:

1. Find why a skill loads twice. Explain which copy will remain and which clients are affected. The `Keep one...` detail flow is missing from the PDF and is a priority to test.
2. Find a specific package among same-name entries and select the correct source.
3. Add it to the intended client and predict all inherited effects before Apply.
4. Move an eligible remote server to a gateway without losing its connection. Explain why a local-only server stays on the Mac.
5. After an unrelated task, find the earlier change, read its result, and Undo it.
6. Recover from a stale preview or lost result, then complete one task by keyboard at increased zoom.

Record completion without help, wrong item/client selections, wrong predictions, backtracking, time to a correct decision, and successful recovery. After each task ask for effort on a 1-7 scale and confidence in what changed. At the end ask what felt safe, confusing, and worth using again.

Provisional design goals: identify the first useful action within about 10 seconds; no unintended target-client selection; find Undo within about 10 seconds; no false assumptions that a saved change is already running. Establish the baseline first and revise these goals from observed tasks. They are not published industry thresholds.

For this local utility, more time spent in the product is not a success metric. Fast, confident completion and a clear exit are better goals. Run moderated sessions or use explicit opt-in feedback; do not add telemetry as a side effect of this audit.

## Suggested order of work

1. **Trust and decisions:** truthful uncertain-result copy; correct scope and freshness; all affected clients in Add/Preview; exact saved/restart states; safe gateway action; reproduced keyboard blockers.
2. **Readability and discovery:** item/source width, descriptions, Details affordance, contextual search, neutral local/direct states.
3. **Interaction polish:** remove forced waits and repeated stagger, improve success contrast and key hit areas, verify focus and rapid interactions.
4. **Validate:** run the task study and one bounded accessibility/performance pass. Refine based on actual obstacles.

Keep the current five main destinations until a navigation test demonstrates a problem. Avoid speculative modes, a new command system, a new animation library, or a mandatory tour. Optional filters should earn their place through a real task.

## Implementation and browser evidence

Assessment B ran the app on copied test fixtures at 1280 x 720 in dark theme. The app used an explicit sandbox home, explicit configuration adapters, and a runner that refused external commands. No real client settings were used. The temporary server and tab were closed after the checks.

### Reproduced successfully

- A keyboard-opened item panel was instant and received focus.
- Preview kept the current state until Apply.
- Apply produced a verified journal entry and a backup; the table changed to the new state.
- Focus returned to the original row after Apply.
- Changes retained Undo after the temporary toast.
- Undo produced an undone journal entry. The resulting configuration matched the backup byte for byte.

This establishes one representative successful cycle, not every operation or failure mode.

### Reproduced defects

- Tab changes dropped keyboard focus to BODY.
- The Review footer focus loop omitted the file-change summary.

### Source-confirmed risks requiring targeted fault tests

- A lost Apply response can produce the false claim that no change happened.
- Refresh failure can leave stale data under a fresh timestamp or different selected project.
- Gateway connections are collected globally in `gateway_view.py:55-59`, without filtering to the displayed gateway and effective scope. `gateway.js:230` gives this list to the shown gateway card. With two gateways, disabled entries, or project-specific connections, the diagram may imply the wrong route. Reproduce these cases and scope the data before changing the graph's appearance.
- The Apply completion floor remains under reduced motion.

### PDF differences

- Discover's current first column measured 344.42 px of a 1016 px table, about 34%. The PDF's narrower appearance should not be reported as the current layout. Single-line truncation and source distinction still deserve a realistic long-name fixture.
- The PDF gateway shows apparently inconsistent lines/count and empty client tiles. This was not reproduced. Current line/count rendering uses the same connection list; SVG icon assets are explicitly referenced and exist. Do not conflate that screenshot observation with the separate multiple-gateway data risk.
- Overview's four clients versus three Load map columns has an explicit implementation reason: Desktop Code-tab entries appear in the Claude Code column as `Desktop app`. Explain this relationship when useful; it is not an unexplained missing client in the data model.

### Detector limits

The detector ran once and returned two `layout-transition` warnings. It fell back to regex mode because its parser dependencies were unavailable. It did not establish computed contrast, selector-level correctness, or accessibility compliance.

- `style.css:213`: real width animation on a small absolutely positioned switch thumb. No observed frame problem; lower priority than functional findings.
- `style.css:326`: false positive for SVG `stroke-width`, not layout width.

No visual detector overlay was injected because the supported evaluation API was read-only. No mobile, browser zoom, screen reader, reduced-motion emulation, network fault injection, or frame-time profile was performed. The full automated test suite was not run for this read-only product audit.
